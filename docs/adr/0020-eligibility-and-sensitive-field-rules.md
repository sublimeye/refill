# ADR 0020: Eligibility and sensitive-field rules (word semantics, bounded walks, fail closed)

## Context
Spec 5.2 (eligibility) and 5.3 (never-capture list) run in the content script against hostile page content, for both record and fill. Two failure modes matter: a sensitive field captured or filled (leak), and an ordinary field refused (silent usability loss). The brief's keyword list (`pass(word)?`, `pin`, `token`, ...) needs concrete matching semantics, and the eligibility checks need budgets.

## Decision
- Both modules (`src/lib/fields/eligibility.ts`, `sensitive.ts`) are DOM-only with zero runtime dependencies. Neither throws: `isEligible` returns false and `isSensitive` returns true on any exception (a page-replaced getter, a cross-origin error).
- Eligibility is cheap and ordered: kind, connected, top window, `:disabled` (also true under a disabled `fieldset`), readonly, an `[inert]` / `[aria-hidden="true"]` walk over the element and its ancestors (crossing shadow hosts), then one `checkVisibility`, one `getBoundingClientRect`, the document-area test, the near-invisible test, and `elementFromPoint` only when the box intersects the viewport. `[aria-hidden]` is compared case- and whitespace-insensitively (`TRUE`, ` true ` hide the subtree in the accessibility tree). The ancestor walk is capped at 512 levels; a deeper chain is ineligible.
- When the box is only partly in the viewport the hit test uses the center of the visible part (the real center may be off-screen, where `elementFromPoint` returns null). Inside a shadow tree the hit test asks the control's own `ShadowRoot`, because the document-level answer is retargeted to the host and cannot tell the control from a covering sibling.
- Node type checks use `localName` / `nodeType`, not `instanceof`, so a control from another realm is classified correctly.
- `isEligible(el, doc, isTopWindow)` takes the top-window predicate as a third parameter, defaulting to `win === win.top`. Vitest browser mode runs every test in an iframe, so tests stub it and exercise the real default with a nested iframe.
- Name/id/label matching: the string is capped at 256, camelCase and leading-acronym boundaries are split (`PINCode` to `PIN Code`, `txtCVVCode`, `SSNLast4`, `CCNumber`), lowercased, and every non-alphanumeric run (`_`, `$`, `-`, `[`) becomes a space. Then:
  - whole-word match: `pass`, `pwd`, `pin`, `2fa`, `mfa`, `cvv`, `cvc`, `csc`, `ssn`, `seed`, `nonce`, and the phrases `verification code`, `security code`, `social security`, `recovery phrase`, `card number`. So `pin` does not hit `pinnacle` or `spinner`; `pass` does not hit `passenger`, `bypass`, `compass`; `seed` does not hit `seeded`.
  - `token` / `tokens` may end a word but not start one (`csrf_token`, `authenticity_token`, `__RequestVerificationToken`, `accesstoken` hit; `tokenized`, `tokenizer` do not). `otp` may start a word (`otp_code`, `otpcode`) but not appear inside one (`motp`).
  - separator-free substring for long unambiguous forms: `password`, `passwd`, `passcode`, `passphrase`, `mnemonic`, `viewstate`, `eventvalidation`, `csrf`, `xsrf`, `totp`, `cardnumber` (so `confirmpassword`, `__VIEWSTATE`, `csrfmiddlewaretoken` hit).
  - `captcha` as a substring of name, id, label or class.
  - Every pattern is an alternation of literals and bounded classes, linear on a 256-character input. The id is read raw, not from `Sig.idStable`, which is null for generated ids such as `password1234`.
  - `code` is sensitive only after an allow-listed qualifier: sms, text, verify, verification, auth, authentication, authenticator, one time / onetime, otc, 2fa / twofa, two factor, mfa, login, security, card, cc, access, confirmation (`smsCode`, `oneTimeCode`, `cardCode`, Authorize.net's `x_card_code` CVV field); `pin` code is covered by the whole word `pin`. Also the exact name or label `code` / `otc`, and the labels "6-digit code", "code we sent", "we sent a code" and "enter (your / the) code" ("enter promo code" and "enter your zip code" stay capturable). `zip`, `postal`, `promo`, `coupon`, `area`, `country`, `discount` and `referral` codes stay capturable. `confirmation code` is included (the emailed sign-up code); `confirm code` is not (ambiguous). Card-number names also match `cc num(ber)`, `card no` and `card num`.
  - Unsplit `pincode` (Indian postal code) stays capturable; `pin_code`, `pinCode` and the label "PIN code" are sensitive (an over-match that only costs a non-capture).
- `autocomplete` is checked per token, so a section prefix (`section-pay cc-number`) does not hide a sensitive token.
- `-webkit-text-security` is read from the computed style; anything other than empty or `none` is sensitive.
- `PasswordHistory` observes the `type` attribute with `subtree`, `attributeFilter: ["type"]` and `attributeOldValue` (a flip to password and back before the callback runs is still seen), sweeps `input[type=password]` at `observe` time, drains `takeRecords()` on every `wasPassword` call so a toggle in the same task is not missed, and keeps membership in a `WeakSet`. `observe` accepts a `Document` or a `ShadowRoot` (a document observer does not see inside shadow trees). `disconnect()` stops observing and keeps what was seen.
- `looksLikeCardNumber` slices the value to 64 characters before stripping spaces and dashes, then requires 13 to 19 digits, Luhn, and a card hint (`card`, `credit`, `debit`, `ccnum`, or a standalone `cc` token in name, stable id, label or autocomplete) or an IIN prefix (4, 51-55, 2221-2720, 34, 37, 6011, 65).

- Horizontal position (controller ruling): the box must overlap `[0, viewport width]` in document coordinates (`scrollX` accounted for), with the viewport width taken from the scrolling element (`document.scrollingElement`, which is `body` in quirks mode and `html` otherwise; `documentElement.clientHeight` is the document height in quirks mode and broke every below-the-fold field on doctype-less pages). A right-parked decoy (`left: 9999px`, `translateX(10000px)`, with or without `overflow-x: hidden`) is ineligible; `scrollWidth` is not used, because such a decoy grows it by itself. Vertically the box may be anywhere within the document's scroll height. A real field past the right edge of the initial viewport is not filled (fail closed).
- Scroll containers (ruling P12, app-shell SPAs where `html,body{overflow:hidden}` and an inner `#app{overflow:auto}` holds the page): a single bounded ancestor pass finds every scrolling ancestor that actually overflows (computed `overflow-x/y` auto, scroll or overlay and `scrollHeight > clientHeight` or `scrollWidth > clientWidth`; `html` and `body` excluded, they are the document rule's). The control must lie inside each container's scrollable content (vertically anywhere in its scroll height, horizontally over `[0, clientWidth]`, scroll offset accounted for), which is P10 applied per container; the outermost container's own box then has to pass the document rule. This extends the ruling's "nearest container": a decoy inside a small scroller that is itself parked off-canvas is still rejected. The hit test runs on the part of the box inside the viewport and every container's client box. With no scrolling ancestor the document rule applies to the control. When `scrollingElement` is null (quirks mode with overflow set on both `html` and `body`) the viewport is `innerWidth` / `innerHeight`.
- Custom-styled checkbox and radio (ruling P13): a native checkbox or radio that fails only the opacity (`opacity: 0`, faint ancestor), size (< 4x4, sr-only) or hit-test (covered by its styled sibling) checks is still eligible when at least one of its `labels` (at most 16) passes `checkVisibility`, no `inert`/`aria-hidden` ancestor, size >= 4x4, the scroll-container/document position rules and the opacity rule. `display:none`, `visibility:hidden`, `content-visibility`, disabled, readonly, inert/aria-hidden and off-canvas controls stay ineligible regardless of labels. Fill must use `.click()` (the label proxy) for these (Plan 3, Task 10). Selects and text controls stay strict: custom dropdowns are unsupported widgets.
- Transparent-text rule exemption (N2): `date`, `time`, `datetime-local`, `month` and `week` inputs, where `color: transparent` hides the empty `mm/dd/yyyy` placeholder under a floating label. Only `date` is an eligible kind today.
- Near-invisible styling (ruling P11), one `getComputedStyle` per ancestor over the bounded chain: effective opacity (the product of `opacity` and any `filter: opacity(n)` factor) below 0.1; and, for text-entry controls and selects (not native checkbox/radio, which paint regardless of color), computed text color alpha 0 AND background color alpha 0 AND no background image (the image clause is ours, so a custom-styled field with a gradient background is not rejected).

## Consequences
- Over-matching is the safe direction and is accepted for the substring family (a field named `mypasswordhint` is never captured); ordinary words are protected by the whole-word rule. A field whose only cue is an unsplit lowercase compound such as `userpin` is not caught by the name rule (autocomplete, type and label still apply).
- Accepted residual risk (also spec 8.3): `mask-image` hiding, an opaque overlay with `pointer-events: none` (`elementFromPoint` ignores it, and floating labels need it to pass), a field below the fold covered by another element (the hit test only runs in the viewport), and font-based masking (`font-family: text-security-disc`). A honeypot needs a hostile same-origin page, which can already read filled values (spec 8.3), and step matching limits what it can harvest.
- A field in an `overflow: auto` container scrolled out of view is eligible while it is inside the container's scroll height (it is reachable by scrolling). A show-password toggle that replaces the element with a new `type=text` input is not recognized as was-password.
- A card number longer than 64 characters of padding is judged on its first 64 characters, which can only cause a drop (safe), never a capture.

## Status
Accepted.
