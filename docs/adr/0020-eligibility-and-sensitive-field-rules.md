# ADR 0020: Eligibility and sensitive-field rules (word semantics, bounded walks, fail closed)

## Context
Spec 5.2 (eligibility) and 5.3 (never-capture list) run in the content script against hostile page content, for both record and fill. Two failure modes matter: a sensitive field captured or filled (leak), and an ordinary field refused (silent usability loss). The brief's keyword list (`pass(word)?`, `pin`, `token`, ...) needs concrete matching semantics, and the eligibility checks need budgets.

## Decision
- Both modules (`src/lib/fields/eligibility.ts`, `sensitive.ts`) are DOM-only with zero runtime dependencies. Neither throws: `isEligible` returns false and `isSensitive` returns true on any exception (a page-replaced getter, a cross-origin error).
- Eligibility is cheap and ordered: kind, connected, top window, `:disabled` (also true under a disabled `fieldset`), readonly, an `[inert]` / `[aria-hidden="true"]` walk over the element and its ancestors (crossing shadow hosts), then one `checkVisibility`, one `getBoundingClientRect`, the document-area test, the near-invisible test, and `elementFromPoint` only when the box intersects the viewport. `[aria-hidden]` is compared case- and whitespace-insensitively (`TRUE`, ` true ` hide the subtree in the accessibility tree). The ancestor walk is capped at 512 levels; a deeper chain is ineligible.
- When the box is only partly in the viewport the hit test uses the center of the visible part (the real center may be off-screen, where `elementFromPoint` returns null). Inside a shadow tree the hit test asks the control's own `ShadowRoot`, because the document-level answer is retargeted to the host and cannot tell the control from a covering sibling.
- Node type checks use `localName` / `nodeType`, not `instanceof`, so a control from another realm is classified correctly.
- `isEligible(el, doc, isTopWindow)` takes the top-window predicate as a third parameter, defaulting to `win === win.top`. Vitest browser mode runs every test in an iframe, so tests stub it and exercise the real default with a nested iframe.
- Name/id/label matching: the string is capped at 256, camelCase and leading-acronym boundaries are split (`PINCode` to `PIN Code`, `txtCVVCode`), lowercased, and every non-alphanumeric run (`_`, `$`, `-`, `[`) becomes a space. Then:
  - whole-word match: `pass`, `pwd`, `pin`, `2fa`, `mfa`, `cvv`, `cvc`, `csc`, `seed`, `nonce`, and the phrases `verification code`, `security code`, `recovery phrase`. (`ssn`, `social security` and `card number` were withdrawn by the 2026-10-27 amendment.) So `pin` does not hit `pinnacle` or `spinner`; `pass` does not hit `passenger`, `bypass`, `compass`; `seed` does not hit `seeded`.
  - `token` / `tokens` may end a word but not start one (`csrf_token`, `authenticity_token`, `__RequestVerificationToken`, `accesstoken` hit; `tokenized`, `tokenizer` do not). `otp` may start a word (`otp_code`, `otpcode`) but not appear inside one (`motp`).
  - separator-free substring for long unambiguous forms: `password`, `passwd`, `passcode`, `passphrase`, `mnemonic`, `viewstate`, `eventvalidation`, `csrf`, `xsrf`, `totp` (so `confirmpassword`, `__VIEWSTATE`, `csrfmiddlewaretoken` hit).
  - `captcha` as a substring of name, id, label or class.
  - Every pattern is an alternation of literals and bounded classes, linear on a 256-character input. The id is read raw, not from `Sig.idStable`, which is null for generated ids such as `password1234`.
  - `code` is sensitive only after an allow-listed qualifier: sms, text, verify, verification, auth, authentication, authenticator, one time / onetime, otc, 2fa / twofa, two factor, mfa, login, security, card, cc, access, confirmation (`smsCode`, `oneTimeCode`, `cardCode`, Authorize.net's `x_card_code` CVV field); `pin` code is covered by the whole word `pin`. Also the exact name or label `code` / `otc`, and the labels "6-digit code", "code we sent", "we sent a code" and "enter (your / the) code" ("enter promo code" and "enter your zip code" stay capturable). `zip`, `postal`, `promo`, `coupon`, `area`, `country`, `discount` and `referral` codes stay capturable. `confirmation code` is included (the emailed sign-up code); `confirm code` is not (ambiguous).
  - Unsplit `pincode` (Indian postal code) stays capturable; `pin_code`, `pinCode` and the label "PIN code" are sensitive (an over-match that only costs a non-capture).
- `autocomplete` is checked per token, so a section prefix (`section-pay cc-csc`) does not hide a sensitive token. Sensitive tokens: `current-password`, `new-password`, `one-time-code`, `cc-csc` (the other `cc-*` tokens were sensitive until the 2026-10-27 amendment).
- `-webkit-text-security` is read from the computed style; anything other than empty or `none` is sensitive.
- `PasswordHistory` observes the `type` attribute with `subtree`, `attributeFilter: ["type"]` and `attributeOldValue` (a flip to password and back before the callback runs is still seen), sweeps `input[type=password]` at `observe` time, drains `takeRecords()` on every `wasPassword` call so a toggle in the same task is not missed, and keeps membership in a `WeakSet`. `observe` accepts a `Document` or a `ShadowRoot` (a document observer does not see inside shadow trees). `disconnect()` stops observing and keeps what was seen.
- `looksLikeCardNumber` (value-based card detection) was removed by the 2026-10-27 amendment.

- Horizontal position (controller ruling): the box must overlap `[0, viewport width]` in document coordinates (`scrollX` accounted for), with the viewport width taken from the scrolling element (`document.scrollingElement`, which is `body` in quirks mode and `html` otherwise; `documentElement.clientHeight` is the document height in quirks mode and broke every below-the-fold field on doctype-less pages). A right-parked decoy (`left: 9999px`, `translateX(10000px)`, with or without `overflow-x: hidden`) is ineligible; `scrollWidth` is not used, because such a decoy grows it by itself. Vertically the box may be anywhere within the document's scroll height. A real field past the right edge of the initial viewport is not filled (fail closed).
- Scroll containers (ruling P12, app-shell SPAs where `html,body{overflow:hidden}` and an inner `#app{overflow:auto}` holds the page): a single bounded ancestor pass finds every scrolling ancestor that actually overflows (computed `overflow-x/y` auto, scroll or overlay and `scrollHeight > clientHeight` or `scrollWidth > clientWidth`; `html` and the document's `scrollingElement` are excluded, they are the document rule's; `body` is a container when `html`'s overflow is not `visible` in both axes, because then body's overflow no longer propagates to the viewport: `html{overflow:hidden} body{overflow:auto}` and `html,body{overflow:auto}` shells, standards and quirks). The control must lie inside each container's scrollable content (vertically anywhere in its scroll height, horizontally within the container's currently visible slice `[0, clientWidth]` (N8: the visible carousel slide is eligible, off-screen slides are not; the page itself keeps the document-coordinates band), which is P10 applied per container; the outermost container's own box then has to pass the document rule. This extends the ruling's "nearest container": a decoy inside a small scroller that is itself parked off-canvas is still rejected. The hit test runs on the part of the box inside the viewport and every container's client box. Decoy guard (N6): a container whose client box is under 8 px on a side (a classic scrollbar alone takes up to 15 px, so a 4x4 `overflow:auto` box paints nothing; stricter than the ruled 4 px) rejects, and so does a container that clips the box to less than 4x4 px; a box scrolled entirely out of its container is judged by the scroll rules only. With no scrolling ancestor the document rule applies to the control. When `scrollingElement` is null (quirks mode with overflow set on both `html` and `body`) the viewport is `innerWidth` / `innerHeight`.
- Custom-styled checkbox and radio (ruling P13): a native checkbox or radio that fails only the opacity (`opacity: 0`, faint ancestor), size (< 4x4, sr-only) or hit-test (covered by its styled sibling) checks is still eligible when at least one of its `labels` (at most 16) passes `checkVisibility`, no `inert`/`aria-hidden` ancestor, size >= 4x4, the scroll-container/document position rules and the opacity rule. `display:none`, `visibility:hidden`, `content-visibility`, disabled, readonly, inert/aria-hidden and off-canvas controls stay ineligible regardless of labels. Fill must use `.click()` (the label proxy) for these (Plan 3, Task 10). The label runs the control's checks (N7): visibility, size, opacity, transparent text on a transparent background, position, container clipping (>= 4x4 painted) and the hit test where it is in the viewport (the invisible control itself lying over the label is fine). Residual: a label below the fold cannot be hit-tested, so a covered or hidden label there still passes (also spec 8.3); the exposure is a boolean the user did not see, never a text value. Selects and text controls stay strict: custom dropdowns are unsupported widgets.
- Transparent-text rule exemption (N2): `date`, `time`, `datetime-local`, `month` and `week` inputs, where `color: transparent` hides the empty `mm/dd/yyyy` placeholder under a floating label. Only `date` is an eligible kind today.
- Near-invisible styling (ruling P11), one `getComputedStyle` per ancestor over the bounded chain: effective opacity (the product of `opacity` and any `filter: opacity(n)` factor) below 0.1; and, for text-entry controls and selects (not native checkbox/radio, which paint regardless of color), computed text color alpha 0 AND background color alpha 0 AND no background image (the image clause is ours, so a custom-styled field with a gradient background is not rejected).

## Consequences
- Over-matching is the safe direction and is accepted for the substring family (a field named `mypasswordhint` is never captured); ordinary words are protected by the whole-word rule. A field whose only cue is an unsplit lowercase compound such as `userpin` is not caught by the name rule (autocomplete, type and label still apply).
- Accepted residual risk (also spec 8.3): `mask-image` hiding, an opaque overlay with `pointer-events: none` (`elementFromPoint` ignores it, and floating labels need it to pass), a field below the fold covered by another element (the hit test only runs in the viewport), and font-based masking (`font-family: text-security-disc`). A honeypot needs a hostile same-origin page, which can already read filled values (spec 8.3), and step matching limits what it can harvest.
- A field in an `overflow: auto` container scrolled out of view is eligible while it is inside the container's scroll height (it is reachable by scrolling). A show-password toggle that replaces the element with a new `type=text` input is not recognized as was-password.

## Status
Accepted. Amended 2026-10-27 (below).

## Amendment (2026-10-27): only secrets are never captured
**Decision (the user's, 2026-10-27).** Refill saves everything a person types except secrets: passwords, one-time codes, card security codes (CVV) and captchas. Card numbers and SSNs are now saved and filled like any field, and the user can still set any field to "Don't save" on the review page. The earlier exclusion of card numbers and SSNs is withdrawn. Spec 1.2, 1.4, 5.3 and 6.2 are amended to match.

**What changed in the rules** (`src/lib/fields/sensitive-rules.ts`, shared by `isSensitive` in the content script and `sigLooksSensitive` in the worker, so scan, fill and the worker's re-check agree):
- Removed: the words `ssn`, `social security`, `card number` / `card num` / `card no` and `cc num(ber)`, and `cardnumber` from the separator-free forms; every `cc-*` autocomplete token except `cc-csc`; `looksLikeCardNumber` with its IIN and hint helpers and tests (the Luhn heuristic, the 64-character value cap and the "dropped - looked like a card number" review state it fed).
- Kept: `cvv`, `cvc`, `csc`, the card-code qualifiers (`card code`, `cc code`, `x_card_code`, `security code`), `cc-csc`, `pin`, `seed`, `mnemonic`, `recovery phrase`, `passphrase`, the OTP family, captcha and the never-typed fields.
- `sigLooksSensitive` lowercases `sig.type` before comparing, because the worker receives signatures in messages (`type: "PASSWORD"` is a password).

**Why the CVV stays excluded.** Sites ask for the CVV on every payment because it should not be kept, and a card number together with its CVV is the complete fraud set. A stored card number alone is not enough to pay on most sites; number plus CVV is. Keeping the CVV out of the vault keeps a vault compromise short of that set.

**Passwords include recovery phrases and PINs.** A PIN, a passphrase, a seed or mnemonic and a recovery phrase are credentials, so they are treated as passwords and never captured or filled.

**Consequences.** A card number or SSN is encrypted at rest like every captured value, but once filled into a page it is readable by same-origin script (spec 8.3 residual risk, now covering these values too). Card-number auto-detection by value is gone; the rule set now judges the signature only.
