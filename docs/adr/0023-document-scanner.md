# ADR 0023: Document scanner (bounded iterative walk, cap before signatures, shadow roots joined to the password history)

## Context
`scanDocument` feeds both record and fill with the page's eligible, non-sensitive controls (spec 5.1 to 5.3). It runs in the content script on hostile pages, so its cost and its failure behavior matter as much as its output. Task 5 review also asked that the 300-control cap apply before signatures are built for further elements.

## Decision
- `src/lib/fields/scan.ts`: `scanDocument(doc, history, openOrClosedShadowRoot?, isTopWindow?)` and `pageFingerprint` (`sigKey` per control). `isTopWindow` is passed through to `isEligible` and exists for tests only.
- Walk: iterative pre-order (no recursion, so a 20 000-deep chain cannot overflow the stack), document order, light DOM plus shadow roots. A shadow root is read before its host's light children. The callback (`chrome.dom.openOrClosedShadowRoot` in production) supplies closed roots; otherwise `el.shadowRoot`. It is asked only for elements that can host a shadow root (custom elements and the `attachShadow` tag list), not for all 50 000 nodes. A throwing callback skips that host.
- DOM clobbering (fix round 1, ruling P18). A `<form>` exposes its named controls as properties that override its own (LegacyOverrideBuiltIns): `<form><input name="nodeType">` makes `form.nodeType` an element, `name="parentNode"` / `"firstChild"` redirect a tree walk, `name="action"` replaces `form.action`. Review reproduced two failures in Task 5/6 code: a hidden input named `nodeType` ended the ancestor walk at the form, so a field under an `opacity: 0.001` or `aria-hidden` wrapper passed eligibility; one named `parentNode` made `textOf` loop forever inside a label. `src/lib/fields/dom.ts` now holds the prototype accessors (nodeType, parentNode, firstChild, nextSibling, localName, shadowRoot, scroll/client metrics, `hasAttribute`, `getAttribute`, `getBoundingClientRect`) and every read of an element that can be a form goes through them: the scanner's walk and form action (attribute, not `form.action`), `parentOf` / `reachable` / `inspectAncestors` / `paintedRegion` / `controlKind` in eligibility.ts, `textOf` in signature.ts, and the mutation-record handling in sensitive.ts. `textOf`'s climb now spends node budget too. Controls (input, select, textarea) have no named-property getter, so they are read directly. A sweep test renders nine fixtures (faint, aria-hidden and inert wrappers, labels containing forms, aria-labelledby pointing at a form, scroll-container and parked forms) with a hidden input named after each of 36 properties and requires the same verdicts as with a harmless name.
- Bounds: at most `MAX_NODE_VISITS` = 50 000 nodes (elements, text and comments all count), `MAX_CONTROLS` = 300 kept controls and `MAX_SIGNATURES` = 1 200 (4 x 300) `buildSignature` calls. Eligible-but-sensitive controls (OTP, card fields) build a signature before they are rejected and do not count as kept, and a signature costs O(page) through `el.labels`, so without the third bound N such fields cost O(N^2) (10 000 took 1.1 s). Hitting any bound sets `truncated`. `labelText` also skips `el.labels` when no label can point at the control (no id and no wrapping label). Measured locally for 10 000 sensitive fields: about 72 ms without ids, about 180 ms with an id on every field. A page with more than 50 000 nodes before its form is therefore partly unscanned (fail closed). Walk cost measured locally: about 5 ms for 2 000 inputs (300 kept), worst of five runs about 24 ms (cold first run).
- Order per element, cheapest first: `controlKind` (non-null) then `isEligible` then `buildSignature` then `isSensitive`. Once 300 controls are kept, the first further element with a control kind sets `truncated` and ends the walk without any eligibility or signature work. So "truncated" means "another control-shaped element exists", not "another kept control exists" (it can over-report; exactly 300 candidates is not truncated).
- A failure on one element (a page-controlled getter throws) skips that element; the walk continues. An unexpected failure of the walk itself returns what was collected with `truncated: true`. `scanDocument` never throws.
- `ordinal` is the index among kept controls with the same form owner (`el.form`, which honors `form=`), or among formless controls of the document. Skipped controls take no ordinal. The signature is built with the tentative ordinal and the counter advances only when the control is kept. Radios contribute one entry each.
- `formAction`: `new URL(action attribute, doc.baseURI).pathname` for a form with an `action` attribute (an empty attribute resolves to the document); a form without the attribute uses the current document's pathname (the browser submits there); formless is null; an unparsable action is null. `buildSignature` applies the 256 cap.
- Password history: `PasswordHistory.observe(root)` replaces the previous observation, so it cannot be called for each shadow root. New `PasswordHistory.observeShadow(root)` adds a shadow root to the same observer (sweep plus `type` observation), is idempotent per root and resets on `disconnect()`. `scanDocument` calls it for every shadow root it enters, before judging that root's controls. The caller keeps one history per document and calls `observe(document)` once. A toggle that happened in a shadow root before the first scan that entered it is not seen; that control is judged by its current type only.

## Consequences
- Pages with deep or huge DOMs scan partially and report `truncated`; the content script must treat that as "may be incomplete" (no claim of a full page).
- `sensitive.ts` gained one method; existing `observe` semantics are unchanged.
- Named-property shadowing is closed in the field modules listed above, not only in the walk. Remaining reads off page elements are on controls (safe) or on `Document` / `ShadowRoot` (their named properties do not override built-ins). The accessors do not help against a page that replaces prototypes in the same JS world; an isolated-world content script has its own prototypes.
- `dom.ts` reads `Node.prototype` at import, so it (and eligibility / signature / scan) must only be imported where a DOM exists; `match.ts` keeps importing types only.

## Status
Accepted.
