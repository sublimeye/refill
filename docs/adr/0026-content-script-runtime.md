# ADR 0026: Content-script runtime (start guard, re-scan triggers, fill bookkeeping) and the fixture e2e suite

## Context
Plan 2 Task 12 wires the scanner (ADR 0023), the fill engine (ADR 0024) and the content protocol (ADR 0025) into the content script, and adds the fixture e2e suite. The plan fixes the flow (wait for prerender activation, scan, `scan-report`, apply the plan, `fill-result`, 250 ms debounced re-scan, bfcache restore is the same document, stop when the extension context is gone). Controller rulings added: the script must be idempotent with a guard the page cannot pre-set (ADR 0018), re-scan on `scrollend` too (eligibility depends on scroll position, ADR 0020), top frame only, `dom.openOrClosedShadowRoot` for closed roots, no logging of page data. This ADR records the choices left open.

## Decision
- **Module split.** `src/entrypoints/refill-content.ts` does the top-frame check (`window !== window.top`, since `executeScript` can reach frames even though the registration says `allFrames: false`) and the https check, captures the extension API (`captureChrome`, `src/lib/content/chrome-api.ts`, below), and hands `send`, `alive` and the closed-root reader to `startContentScript(scope, env)` in `src/lib/content/runner.ts`. The runner touches no extension API, so browser-mode tests drive it with an injected `send`.
- **`chrome`, captured and checked, not WXT's `browser`.** Window named access reaches the isolated world: on a document's first load in a tab, page markup replaces even the extension globals there (verified on Chromium 156 in a fresh tab: `<form id="browser"><input name="runtime" id="x">` makes `globalThis.browser` the form with `runtime.id === "x"`, `<form id="chrome">` makes `chrome` the form, `<iframe name="chrome">` makes it the frame's window; a document reached by navigating within the same tab keeps the real globals). WXT's `browser` picks `globalThis.browser` whenever `browser.runtime.id` is truthy, so `browser` markup would silently switch Refill off and forge `alive()`. The script therefore reads only `chrome`, once, and starts only if it is a plain object (not a DOM node, not a frame's window) whose `runtime.sendMessage` is a function and whose `runtime.id` is a non-empty string. Anything else fails closed on that load: no scan, no message, and nothing found through named access is ever called. `alive()` reads `id` from the captured runtime object, and `dom.openOrClosedShadowRoot` is captured the same way (optional). The content bundle has no runtime import of `wxt/browser` at all (the runner takes only types from the message protocol), and `pnpm test:manifest` fails if `globalThis.browser` appears in the built `refill-content.js`. A page can always disable Refill on itself this way (accepted, spec §8.3); it cannot make Refill send or fill anything. e2e opens each markup page in a fresh tab: `browser` markup still fills, `chrome` markup leaves no marker, no message and empty fields.
- **Start guard.** `startContentScript(globalThis, …)` sets a flag on the content script's own global object and returns null when it is already set. A registered script and an `executeScript` after enable run in the same isolated world and see the flag; page code shares only the DOM, so it can neither read nor pre-set it. The flag is set before the https check, so a refused start is also final.
- **Re-scan triggers.** One `MutationObserver` (child list, all attributes, character data) on the document plus every shadow root the scan enters (the scanner's shadow-root callback adds each root to the observer once), `scrollend` on the window in the capture phase (catches the non-bubbling `scrollend` of any scroll container), and a persisted `pageshow`. All go through one debounce: 250 ms after the last trigger, but never later than 1 000 ms after the first one (`RESCAN_MAX_WAIT_MS`), so a page that mutates continuously (a ticking clock, an animation) is still re-scanned about once a second. Scans never overlap: a trigger during a scan, or while a plan is awaited, runs exactly one more scan afterwards.
- **What is sent.** A scan is reported only when its fingerprint (`pageFingerprint`, JSON-encoded) differs from the last delivered one, and only when it has controls. The fingerprint is remembered only once the report was delivered (`send` did not throw), so after a failed send the next trigger reports the same page again. A trusted bfcache restore (`pageshow` with `persisted`, `isTrusted`) clears the remembered fingerprint (report again: the vault may have unlocked meanwhile) but keeps the filled ids. A report already in flight then does not re-remember its fingerprint (a reset generation). A `pageshow` the page dispatched itself is ignored: otherwise page script could make the worker match and answer with values once per debounce, at no cost.
- **Applying a plan.** The answer is checked strictly (state `fill`, at most 300 items, each with the five typed fields); anything else, including a router error, does nothing. All items are vetted with `canFill` against the page as it is before the first write. Immediately before each write the control must still mean what was scanned: connected, with the same `name`, `idStable`, `autocomplete`, `type`, `labelText` and `nameIdDerived` as its scanned signature (`buildSignature` again; ordinal and form action are not compared). A framework that re-uses one `<input>` for the next step renames and relabels it in place, and the old step's value must not land there. A mismatch counts as `skipped` and the id is not marked filled; the re-scan reports the element under its new meaning. Then `fillControl` writes (it re-vets the fill rules itself, ADR 0024), all under `withFillingGuard`. A field id is written at most once per document: ids that came back `filled`, `unsupported` or `rejected-by-page` are never attempted again (the latter two would only fail again); ids skipped as not empty or not eligible stay eligible for a later plan (a field that becomes visible later in the same SPA step still fills), and an id named twice in one plan is written once. **While recording** (Plan 3, ruling P20) the rule is per element: a field id is written at most once into each element, so an SPA's Back, which renders the step again as new elements, is pre-filled every time; an element the user edited is still never written, and every fill rule still applies. The runner reads the recording state from the content side's last `record-status` answer; the first plan of a new document arrives before that answer, so it falls under the per-id rule, which is stricter.
- **Counts.** `fill-result` maps outcomes to its three counts: `filled`; `unsupported` = `unsupported` + `rejected-by-page` (both mean "could not fill, needs the user"); `skipped` = everything else, including an item whose index or kind does not match the scan. It is sent only when the plan had at least one item not already filled.
- **Stopping.** A send that rejects with "Extension context invalidated", or any send while `runtime.id` is undefined, stops everything: observers, the password history, listeners, the pending timer. Other send failures (the worker restarting) only skip that cycle. Nothing is logged, not even error names.
- **Hostile DOM.** `addEventListener`/`removeEventListener`, the `prerendering` getter and `PageTransitionEvent.persisted` are captured from the prototypes at import time, as in the field modules (ADR 0023), so the runner never reads a member through an object the page can reach. This is consistency, not a known vector: in the isolated world, window and document members are not shadowed by named elements (a review probe showed `<img name="addEventListener">`, `name="documentElement"` and `name="querySelectorAll"` leave them intact). The vector that does exist is window named access for undefined globals (above). `persisted` throws for a plain `Event` named `pageshow`, which page code can dispatch; that is caught and ignored. If the password history cannot start, the run stops instead of scanning without it (fail closed).
- **E2E profiles from real scans.** Each spec loads its fixture once with no profile, takes the signatures from the content script's real `scan-report` (the service worker seam below), builds the profile from them with test-chosen values keyed by `labelText`, saves it through `__refillE2E.saveProfile`, and reloads. Hand-written `Sig`s were rejected: they would test the matcher against a guess of the scanner's output and drift from it. The cost is that a scanner bug that is consistent between two loads is not caught here (the browser-mode scanner tests cover the scanner itself).
- **E2E service-worker seam.** In the e2e build only, `background.ts` wraps the content handlers and appends one entry per handled `scan-report` (origin, path, tab, document id, the signatures, `truncated`, the plan state and item count) and `fill-result` (the counts) to `__refillE2E.contentLog`. No values are logged. Each entry carries the worker's `boot` id and a `seq`, so specs read "entries since a mark" correctly even if the worker restarts mid-spec (new `boot`, empty log). `__refillE2E.holdReplies()` / `releaseReplies()` hold `scan-report` answers until the spec releases them (the entry is logged first), so a spec changes the page between scan and fill deterministically; a worker restart drops the hold, which fails the spec rather than passing it. Messages the router rejects (frames, unknown origins) never reach a handler and are not logged.
- **Fixture server.** `/billpay/<name>` serves `<name>.html` (the e2e profiles use the prefix `/billpay/`), `/account` serves `account.html`. HTML responses are rendered server side: `{{field}}` becomes the HTML-escaped posted value (empty on GET) and `{{error}}` an error text when a POST lacks `authorize`, so the POST wizard re-renders the user's edited amount the way a WebForms postback does. Bodies are capped at 64 KiB; a POST to a non-HTML file is 405. Fixture page scripts are separate files.
- **No prerender e2e.** Chromium refuses to prerender while DevTools is attached (`PrerenderingDisabledByDevTools`, seen through the CDP `Preload` domain), and Playwright drives every page through DevTools, so a prerendered fixture never prerenders under test. The wait for `prerenderingchange` is covered in the browser-mode runner tests with an injected `isPrerendering`; the default reads the real getter.

## Consequences
- A plan never fills an element whose meaning changed during the round trip (e2e: an input renamed and relabelled in place while the reply is held stays empty).
- A page with markup named `browser` still fills. Markup named `chrome` makes Refill do nothing on that page on a fresh load (fails closed); a page can always disable Refill on itself.
- A second injection is a no-op; the e2e suite proves one `scan-report` per scan cycle after an `executeScript` into a page that already runs the script, and that a frame reached by `executeScript({ allFrames: true })` stops at the top-frame check.
- On a page that mutates continuously the scanner runs about once a second (bounded by the scanner's own budgets, ADR 0023) for as long as the tab is open.
- While recording, a page that re-mounts the same field as a new, empty element gets the recorded value written again (ruling P20); the value is already the page's. Outside recording, a field the user empties after Refill filled it is not filled again in that document; one the user typed into before the scan is not filled, but is filled if the user empties it and the page later changes its fingerprint (it was never written, so the once-per-document rule does not apply).
- Mutations inside a shadow root the scan has not entered yet are only noticed through a document mutation or a scroll; once entered, the root is observed.
- The prerender path is verified only in browser-mode tests, not end to end.

## Amendment (Plan 4, Task 3, 2026-10-29)
- **A nudge reports the page again.** The `refill-nudge` callback re-reads the recording state and, independently, re-scans with the remembered fingerprint forgotten, so an unchanged page is reported again. The worker nudges when its state changes (a recording, an unlock): after an unlock the latest page has to reach it again for the fill (spec §7). The recording's start report (P12) still follows the `record-status` answer.
- **Undo keeps the once-only rule.** Undo (ADR 0036) puts back what Refill wrote, but the field ids stay in the document's filled set: a later plan naming them writes nothing. The user who undid a fill does not get it again on the next DOM change.
- **`fill-result.filled` is the document's running total** of fields Refill filled outside recording and has not undone (the badge's count), capped at 300; after Undo a `fill-result` with all counts 0 is sent. While recording it is that plan's count, as before.
- **The worker's plan is parsed strictly beyond `fill`.** `ask` must be unique integers in 0..299 (at most 300), `gesture.fieldIds` profile ids (`ID_RE`, at most the profile field limit); anything malformed is no plan.
- **Stopping when the extension is gone** shows `updated` first when Refill filled, recorded or showed a notice in this document, and leaves that notice to its own timer (ADR 0036).

## Status
Accepted (2026-10-27). Amended by the Plan 3 final review (2026-10-28, ruling P20): while recording, the once-only key is the field id and the element, not the field id alone. Amended by Plan 4, Task 3 (2026-10-29): the nudge re-report, filled ids staying filled after Undo, the running `fill-result` total and `updated` on the way out.
