# ADR 0024: Fill engine (captured prototypes, guard depth counter, fallback, widgets, framework gate)

## Context
`src/lib/fill/fill.ts` writes vault values into hostile pages (spec 5.5, 5.6). It must work with React and Vue controlled inputs and keystroke-driven masks, must not be steerable by page-defined properties (a form's named controls shadow its own members, React defines an own `value` property on controlled inputs), and must tell the recorder and draft tracker that the resulting `isTrusted` events are not the user.

## Decision
- All DOM members used by the engine, getters, setters and methods alike, are captured from the prototypes at import (`HTMLInputElement` / `HTMLTextAreaElement` / `HTMLSelectElement` `value`, `form`, `HTMLInputElement.checked`, `HTMLSelectElement.options`, `HTMLOptionElement.value`, `HTMLElement` `focus` / `blur` / `click`, `select`, `EventTarget.dispatchEvent`, `Document.execCommand`, `Node.getRootNode`, `Document` / `ShadowRoot` `activeElement`, `ShadowRoot.host`, `Node.baseURI` / `ownerDocument` / `isConnected`, plus the accessors in `fields/dom.ts`) and applied with `.call(el)`. The prototype `value` setter bypasses React's per-node value tracker, so React sees a change on the `input` event.
- Events are plain `new Event(type, { bubbles: true, composed: true })` for `input` and `change` (composed like the native ones, so document-level listeners see events from an open shadow tree) (not `InputEvent`: frameworks key on the event name, and a plain event carries no `data`). Text is `focus`, setter, `input`, `change`, `blur`, then verified through the captured getter.
- Fallback (text kind only): when the value did not stick, `focus`, `select()`, then, only if the control is the deepest focused element, `execCommand("insertText", false, value)` (`"delete"` when the target is empty), `change`, `blur`, verify again; still different is `rejected-by-page`. `execCommand` edits whatever has focus, so a page that moves focus in a `focus` handler, or disables the field on `blur` and focuses the next one, would otherwise receive the value in an unvetted element (cross-origin form, sensitive field, contenteditable). The check is `getRootNode().activeElement === el` and, for each enclosing shadow host up to the document, `host === activeElement` of its own root (`document.activeElement` is only the outermost host for a shadow-DOM input); on failure nothing is inserted and the outcome is `rejected-by-page`. The same helper guards the `restore` path. Only a trusted keystroke-like edit passes a mask that reverts programmatic writes. The guard is held across the whole fill including the fallback.
- Guard: a depth counter released in `finally`, so nested fills and a throwing callback cannot leave it stuck or end an outer guard early. `restore` runs under it.
- `canFill(item, history, origin, isTopWindow?)`: kind matches, `isEligible`, not `isSensitive` (signature built with ordinal 0 and no form action, which the rules do not read), current state empty or equal to `pageDefault` (`String(checked)` for checkbox and radio), and the form owner's `action` attribute resolves against the document base to exactly `origin` (`URL.origin ===`). No `action` attribute means same origin; unparsable or `javascript:` means cross-origin. The attribute is read, never `form.action` (an `<input name="action">` replaces it). `formaction` on a submitter is out of scope. The https-only rule belongs to the registration (ADR 0018) and the caller's `origin`; `canFill` compares exactly and does not re-check the scheme.
- `fillControl(item, history, origin, isTopWindow?)` runs the same rule check as `canFill` (shared `vet`: eligibility, sensitivity, form origin, empty or page default) immediately before writing, since an earlier field's handlers can change `name`, `autocomplete`, `action` or the value, and returns `skipped-ineligible` / `skipped-not-empty` without writing. Vault state, `fillMode` and policy stay with the caller. Never throws. A text or select value the page refuses is put back to the pre-fill value (setter, `input`, `change`) and reported `rejected-by-page`, so no page-mangled copy of the secret stays in the field.
- Checkbox and radio: the value must be exactly `"true"` or `"false"`, anything else is `unsupported` (no click). Native `click()` on the input itself, only when `checked` differs from the target; this is also the label-proxy fill for the opacity-0 pattern (ADR 0020, P13). The click fires `input` and `change` itself. A radio cannot be unchecked by clicking: target `"false"` on an unchecked radio is already satisfied (`filled`, no click), on a checked radio it is `unsupported` (no click). Restoring the radio that was checked unchecks its group.
- Select: the option must exist (captured `options`), else `unsupported`; setter, `input`, `change`, verify.
- Custom widgets are `unsupported`: the control itself has `role=combobox` and is not a native `select`, or one of at most 16 ancestors has `role=combobox` with a popup attached (`aria-haspopup` other than `false`, `aria-controls`, `aria-owns`, or a descendant `[role=listbox]`). A `role=combobox` ancestor with nothing attached does not block a plain input.
- `snapshot` / `restore`: text and select values and checked state before the fill, restored with the same technique under the guard, best effort per control (detached controls are skipped).
- CI gate (Task 5 review carry-over): react, react-dom and vue are devDependencies for the browser-mode fill tests only. `scripts/check-no-frameworks.mjs` fails when any file in the production build contains a React or Vue runtime string (element/portal symbols, fiber and props expando prefixes, devtools hook, client internals name, `__v_isRef`, `__v_skip`, `__vue_app__`, `__vueParentComponent`, `__VUE__`). The marker list was checked against minified production bundles of react-dom and vue; the unit test has one case per marker, and the script fails closed on a missing or empty directory.

## Consequences
- A page whose handler reverts even trusted edits is reported `rejected-by-page`; nothing further is attempted.
- The engine does not detect widgets without ARIA (custom dropdowns built from divs and a hidden input); those are only fillable when the hidden input is eligible, which it is not (selects and text controls stay strict).
- `execCommand` is deprecated but is the only way to produce trusted input events from an extension; if Chromium removes it, the fallback degrades to `rejected-by-page`.

## Status
Accepted.
