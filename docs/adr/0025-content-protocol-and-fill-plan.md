# ADR 0025: Content protocol and the fill-plan handler

## Context
Plan 2 Task 11 opens the router to content scripts, the first messages that come from a context running next to hostile page code. The content script sends a `scan-report` (control signatures, never values) and a `fill-result` (counts); the service worker answers a scan with a fill plan (spec §5.4, §6.3, §7). The plan fixes the message and plan shapes, the caps and the policy rules. This ADR records the choices it leaves open.

## Decision
- **Sender authorization, in this order** (`authorizeContentSender`, after `classifySender` said `content` and the payload parsed): `sender.origin` is canonical (`normalizeOrigin(o) === o`); the site index has a record for exactly that origin with `accessRevoked: false`; `permissions.contains` holds `originPattern(origin)`; `sender.url` parses, is `https:`, and its origin equals `sender.origin`; `sender.tab.id` is a non-negative safe integer. Any miss answers the generic `rejected`. A storage or permissions API failure answers `internal`, never a pass. The default-port pattern grants every port (ADR 0018), so the exact-origin record is what keeps another port of an enabled site out; a test grants every pattern and checks that `https://a.example:8443` is still rejected.
- **Context from the sender only.** Handlers receive `(req, { origin, pathname, tabId, documentId })`, all taken from `sender`; `pathname` is that of `sender.url`. The payload is parsed with exact keys at every level, so an `origin`, `url`, `tabId` or `now` key in a message is a rejection, not an ignored field.
- **Parse before IO.** `parseContentRequest` runs before any store read, so malformed traffic from a page costs no storage access. Caps: at most 300 controls, each `i` a unique integer 0..299, `kind` one of the four `ControlKind`s, every `Sig` with exactly its eight keys, strings at most 256 (or `null` where the type allows), `ordinal` an integer 0..10 000, booleans boolean, `truncated` boolean, fill-result counts integers 0..300. The router's 65 536-char JSON cap runs first. The result is a fresh object.
- **The worker bundle stays DOM-free.** `content-protocol.ts` imports `Sig` and `ControlKind` as types only and keeps its own kind list, so `fields/dom.ts` (which reads `Node.prototype` at import) never loads in the service worker.
- **Fill plan.** `status()` not `unlocked` (including no vault or a corrupt header) → `{ state: "locked" }`; a `LockedError` from `loadProfileForOrigin` (the vault locked between the two calls) → `locked` too; a `lock()` that lands after the DEK was taken (during the storage read or the AES-GCM open, when the captured key still decrypts) → `locked` as well: the handler reads `lockEpoch()` (a generation `vault.ts` changes on every `lock()`) before `status()` and re-checks it after the load and matching, and from that check to the return everything is synchronous, so no lock can land in between; any other load error propagates and the router answers `internal`. No profile, or `profileApplies` false → `{ state: "none" }`. Otherwise **every** saved field takes part in `matchControls`, whatever its policy, and only matched fields with `policy === "save"` become items. An `ask` or `skip` field that also claims a control therefore keeps a `save` field from taking it (the conflict drops both) instead of being silently out-competed.
- **Zero fillable fields is `none`,** in both modes: no toast, no badge count, no write. `gesture` returns `{ state: "gesture", count }` where `count` is the number of matched `save` fields (what Fill now would fill), not `matched.size`, which would also count `ask`/`skip` matches. The gesture reply carries no values.
- **`lastUsedAt` (ruling P22, amending P4)** is written only for a `fill` reply, from the worker clock, at most once per 60 s per profile id (in-memory map; it resets when the worker restarts). The write is off the reply path (fire-and-forget), so a failing or slow store (a held store lock) neither changes nor delays the answer. It is one compare-and-set in the profile store, `touchLastUsed(origin, id, t)`, inside a single `withStoreLock`: read the site record through `tx`; return without writing if it is missing, revoked, or points at another profile id; read and open `p:<id>` through `tx` (`getEncrypted` gained an optional `tx`); parse; set `lastUsedAt`; `putEncrypted(..., tx)`. It never creates a site record. P4's original form (`saveProfile` of a copy read outside the lock) could re-create a site and its profile that a `site-remove` had just deleted, delete a newer profile that replaced it, or revert a same-id edit such as a policy change from `save` to `skip` (review of PR #29); reading inside the lock closes all three. A `LockedError` during the touch is ignored silently; other failures log the error name.
- **`fill-result`** is validated and answered `{ ok: true }`; Plan 2 records nothing (badge and toast are Plan 4).

## Consequences
- `pathPrefix` scopes a profile; it does not isolate it. `pathname` comes from `sender.url`, and same-origin page script can `history.pushState` to any path before a scan, so it can obtain the fill plan of any profile path on its origin. Later tasks must not treat the prefix as a security boundary.
- The signatures in a scan are trusted only as far as the content script's own page is. A hostile same-origin script (or a compromised renderer for an enabled origin) can craft controls whose signatures match every saved field and receive every `save` value of that origin's profile in `auto` mode without a user gesture; with several steps, including every step's controls ties the Jaccard values and opens the step gate to all of them. Each value still goes out at most once (a field claims at most one control, and duplicated signatures tie with margin 0 and claim nothing). Site isolation keeps it to that origin, since `sender.origin`/`url`/`frameId` are browser-set. The mitigations are the content-script fill rules and `gesture` mode (no values until the user acts).
- Revocation or removal in flight: the sender is authorized before the handler's storage reads and decrypt, so a revoke or `site-remove` landing in those milliseconds does not stop that one reply. An already-injected content script lives until reload regardless; the re-check bounds the window but does not remove it.
- There is no per-tab or per-document rate limit on scans. Each costs a header read, two site-index reads, one AES-GCM open and up to 200 × 300 `scoreSig` calls plus sorts. Only our content script (or a compromised renderer) can send; revisit with a per-`tabId`/`documentId` cap when the content script starts sending.
- `touchLastUsed` writes the profile outside `saveProfile`, so `saveProfile` is no longer the only writer of `p:<id>`; both seal under the same AAD and validate with `parseProfile`.
- The throttle lives in worker memory, so a worker that restarts more often than once a minute writes `lastUsedAt` more often; the value is the same kind of timestamp either way.
- `createRouter` now requires `content` handlers; a router built without them would not type-check, rather than silently rejecting content traffic.
- `ControlKind` is listed twice (`fields/eligibility.ts` and `content-protocol.ts`); the `satisfies ControlKind[]` check makes a removed kind a type error, though an added kind must still be added by hand.

## Status
Accepted (2026-10-26).
