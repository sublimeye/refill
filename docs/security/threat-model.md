# Threat model

Maintained with the code (spec §8.5). Sections 1–3 are the baseline copied verbatim from the design
spec (`docs/superpowers/specs/2026-10-26-refill-design.md` §8.1–§8.3); where they diverge, the spec
is authoritative until this file is updated in the same PR as the change (§ references below point into the spec). Section 4 is a STRIDE
analysis per component of the spec §2 architecture. Rows whose control is not built yet say
"Plan N" in the Test column and are filled in as that plan lands.

## 1. Assets
Saved field values, drafts, passphrase, DEK/KEKs, PRF secret, the list of enabled sites (low).

## 2. Adversaries (in scope)
Hostile web pages; compromised/XSS'd target site; malicious other extensions; local attacker with
**read** access to the browser profile on disk (stolen disk/backup); supply-chain attacker (npm);
hijacked publisher account / malicious update.

A local attacker with **write** access can patch the extension itself and is out of scope, but
cheap tamper-evidence is in scope: the plaintext `draftPub`, lock policy and KDF params are
duplicated inside `vault:integrity` (encrypted, AAD-bound) and compared at every unlock; a mismatch
forces the passphrase path, restores the encrypted values and warns the user. Plaintext values
are treated as hints while locked.

## 3. Out of scope / accepted residual risk
- Malware with OS-level access (keyloggers, memory readers).
- Scripts on the *same* origin reading values after Refill fills them. With Auto mode this happens
  without a user action; mitigated (visible, eligible, current-step, once-per-document,
  same-origin form action) to roughly the exposure of typing it yourself. Users can set a profile
  to One gesture.
- DEK raw bytes in `storage.session` RAM may be paged to disk; any Refill extension page can read
  them (see §4.3).
- **Touch ID is not device-bound.** PRF on macOS comes from iCloud Keychain passkeys, which sync
  across the user's Apple ID devices. Anyone who controls the Apple ID (and a device on it) plus a
  copy of the vault data could unlock without the passphrase. Disclosed in the Touch ID enable
  screen; passphrase-only remains available.
- Ciphertext rollback (restoring an older encrypted record) by a disk-write attacker is not
  detected.
- LevelDB may retain deleted ciphertext until compaction (ciphertext only).

## 4. STRIDE per component

S spoofing · T tampering · R repudiation · I information disclosure · D denial of service ·
E elevation of privilege. Repudiation is not applicable to a single-user local tool and is noted
only where an audit trail matters. "Plan N" means the control and its test land in that plan
(Plan 1 foundation, 2 sites and scan/fill, 3 recorder and review, 4 return visit and toast,
5 drafts, 6 pages/design/export, 7 hardening and release).

Status after Plan 1: the rows for `vault/`, `crypto/`, `store/`, `router/`, the lock triggers and
the onboarding/popup pages are built and name the test file that proves each control. Tests are
under `tests/unit/` (`pnpm test`), `tests/e2e/` (`pnpm test:e2e`, real Chromium) and
`tests/manifest/` (`pnpm test:manifest`). Where a control has no automated test yet, the Test
column says so. ADR numbers point into `docs/adr/`.

| `vault/` (create/unlock, KDF, wrap, integrity, backoff) | **S** attacker guesses the passphrase offline from a stolen profile. **T** disk-write attacker edits the plaintext header (KDF params, lock policy, `draftPub`, wrapped keys) or the integrity record. **I** DEK or passphrase lingers in memory or storage. **D** online brute force through the unlock UI; a corrupt header hangs or crashes unlock. **E** a page or content script triggers unlock or admin operations. | Argon2id via `hash-wasm` (floor m = 65536 KiB, t ≥ 3, p = 1, 16-byte salt; calibrated to ≥ 500 ms, t ≤ 20), parameters bounds-checked before use (`isKdfParams`, ADR 0001). Passphrases NFC-normalised and ≥ 12 code points (`rules.ts`, ADR 0015). Header parsed as untrusted input: exact keys, fixed ciphertext lengths, canonical `draftPub`, else status `corrupt` (ADR 0012). `lock`, `kdf` and `draftPub` duplicated in `vault:integrity` (AES-GCM, AAD `refill/v1\|integrity`) and compared at every unlock: mismatch restores them and returns `warning: "integrity-restored"`; a missing or undecryptable integrity record fails closed (`corrupt`, stays locked). Failed unlocks back off 1 s doubling to 60 s, state in `storage.session`, checked before the KDF runs, deadline clamped to 60 s so a moved clock cannot lock the user out. Unlock and change-passphrase run inside `withStoreLock`, so concurrent guesses are serialized. `lock()` always wins a race with an in-flight unlock (epoch counter, ADR 0012). Raw DEK bytes are zeroed after import; the in-memory key is non-extractable. Unlock is reachable only from extension-page messages (router row). | `tests/unit/crypto/kdf.test.ts` (external Argon2id vector, `RangeError` on out-of-bounds params, calibration floor and cap); `tests/unit/vault/vault.test.ts` (create/unlock/lock round trips, weak and NFC/NFD passphrases, concurrent create, wrong passphrase, corrupt-header cases, backoff without running the KDF, integrity restore and fail-closed, change passphrase, lock-wins-race cases); `tests/unit/vault/header.test.ts` (strict parsing); `tests/unit/vault/backoff.test.ts`; `tests/unit/passphrase/strength.test.ts`; `tests/e2e/vault.spec.ts` (create, lock, unlock in real Chromium). ADR 0001, 0012, 0015. Plan 7: release audit. |
| `crypto/` (AES-GCM, ECDH sealing, HKDF, AAD) | **T** ciphertext modified, truncated, or swapped between records or slots. **I** IV reuse or weak key derivation leaks plaintext relations; error details become a decryption oracle. **E** other modules call WebCrypto ad hoc and skip AAD. | AES-256-GCM, fresh random 96-bit IV per `seal`, 128-bit tag, exactly 12-byte IV and 32-byte keys enforced (`aead.ts`). Every ciphertext is bound to its slot by AAD built in `aad.ts` by convention: `seal`/`open` and `putEncrypted` accept caller-supplied AAD bytes, and no rule or type forces callers through `aad.*`, so this is reviewed, not enforced. Live builders: `refill/v1\|dek\|pw`, `draft-priv`, `integrity`, `draft\|<id>\|<expiresAt or none>`; `profile\|<id>\|<origin>` and `dek\|prf\|<credentialId>` exist but have no caller yet (first used in Plan 3 and Plan 6). Ids containing `\|` are rejected. All decrypt failures collapse to one uninformative `DecryptError` (ADR 0008). Strict canonical base64. HKDF-SHA256 (`hkdf.ts`, RFC 5869 vector) for draft keys (the PRF KEK derivation is Plan 6); draft sealing is ephemeral-ECDH P-256 → HKDF → AES-GCM, public JWK validated (no `d`, P-256 only; ADR 0010). `crypto.subtle` allowed only in `src/lib/crypto/` (Semgrep `refill-subtle-only-in-crypto`, `refill-svelte-no-subtle`). | `tests/unit/crypto/aead.test.ts` (known answer, wrong AAD, wrong key, flipped byte, truncation, malformed IV or base64, IV uniqueness, 32-byte key rule); `tests/unit/crypto/hkdf.test.ts`; `tests/unit/crypto/bytes.test.ts` (strict base64, canonical JSON, AAD literals and `\|` rejection); `tests/unit/crypto/draft-seal.test.ts` (independent key-schedule derivation, swapped `eph`/id/`expiresAt`, wrong recipient, private-JWK rejection). CI: Semgrep rules (`scripts/semgrep.sh scan`). ADR 0008, 0010. |
| `store/` (single write queue over `storage.local`) | **T** concurrent read-modify-write corrupts records; a lock job is bypassed by an unrelated write; ciphertext swapped or rolled back on disk. **I** plaintext secrets written next to ciphertext. **D** a job that awaits a public write deadlocks the queue; quota exhaustion. **E** any module or page writes arbitrary keys. | One FIFO promise-chain queue; `setItems`/`removeItems` always enqueue; `withStoreLock(job)` gives the job a `StoreTx` handle that is closed when the job settles, so a leaked handle cannot write outside the lock (ADR 0011). `storage.local` accessed only from `src/lib/store/` (Semgrep `refill-storage-local-only-in-store`, `refill-svelte-no-storage-local`); `storage.sync` banned (`refill-no-sync-storage`, `refill-svelte-no-sync-storage`). Only vault code writes today, and what it writes is ciphertext plus the documented plaintext header. There is no runtime key whitelist: the `KEYS` and prefix builders are a convention, not an enforcement. Ciphertext rollback is an accepted residual risk (§3). Draft quotas and eviction are Plan 5; quota exhaustion has no Plan 1 control. | `tests/unit/store/queue.test.ts` (FIFO, rejected job does not stall); `tests/unit/store/local.test.ts` (50 synchronous and 10 staggered locked increments, one winner among racing check-then-write jobs, unrelated write waits for a held lock, leaked `tx` rejects, lock released after a throw); `tests/unit/vault/records.test.ts` (ciphertext only at rest). CI: Semgrep rules. ADR 0011. Plan 5: quota eviction. |
| `sites/` (optional host permissions ⇄ registered content scripts) | **S** lookalike / punycode origin or http downgrade treated as the enabled site. **T** stale registration after revoke. **E** broad host access, scripts injected on pages the user did not enable. | Exact-origin https matching only; host access requested per site at user gesture via `optional_host_permissions`; reconciler removes scripts when permission is revoked; manifest has no `<all_urls>`, `tabs`, `webRequest`, `cookies`, `history`, `nativeMessaging`. Plan 1 ships only the manifest part: permissions exactly `storage, activeTab, scripting, alarms, idle`, no host permissions granted at install, no content scripts registered. | Plan 2: reconciler tests, lookalike/punycode/http e2e fixtures. | `router/` (typed messages, sender validation; `src/lib/messaging/`) | **S** content script, web page or another extension forges a page-only or admin message. **T** malformed, oversized or prototype-polluting payloads; a `now` smuggled into a message to defeat backoff or lock deadlines. **E** page-reachable messages invoke vault operations. **D** message flooding. **I** error details leak to the caller. | `externally_connectable` is `{ids: [], matches: []}` and there is no `onMessageExternal` listener. `classifySender` (`router.ts`) returns `page` only for this extension's id with an extension URL (a popup, or a tab whose URL is `chrome-extension://<id>/…`; a page framed inside a web page is not a page), and `content` only for an https top-frame (`frameId 0`) sender with a tab; a falsy runtime id classifies nothing. All four vault messages are page-only; `ContentRequest` is `never`, so every content-classified message is rejected until Plan 2. Messages over 65 536 JSON characters, with extra keys, a non-plain object, a `__proto__` key, or a string over 1024 units are rejected with a generic `{ok:false,error:"rejected"}`; handler failures answer `internal` and log the error name only. Origin comes from `sender`, never from the payload. Registered synchronously at worker start (ADR 0013, 0014). | `tests/unit/messaging/router.test.ts` (sender classification incl. foreign id, framed page, falsy id, http, subframe; strict parsing, extra keys, timestamp rejection, size caps, content-script sender refused for `vault-unlock`; generic errors; `sendResponse` adapter; `sendToSw` errors); `tests/unit/messaging/background.test.ts` (listener registered in the first turn, foreign sender rejected); `tests/e2e/smoke.spec.ts` (real service worker answers page messages and rejects invalid ones); `tests/manifest/manifest.test.ts` (`externally_connectable`). ADR 0014. Plan 7: spoofed-origin and admin-message e2e from a real content script. |
| Lock triggers (`vault/lock-triggers.ts`) | **I** an unlocked session outlives the user's presence, the screen lock or a worker restart. **D** a stale alarm or a late wake locks a fresh unlock. **T** a forged `now` extends a session. | Screen lock or idle ≥ 15 min (`idle.setDetectionInterval(idleMinutes * 60)`) locks; a hard-max alarm at `unlockedAt + 12 h` locks; passphrase required every 14 days. On every worker start `enforceOnWake` checks the session through `lockIfExpired` (locks only a session that is really expired, never on uncertainty) and re-arms idle and alarm. `status()` and `getDek()` apply the same hard-max check on stale reads without cancelling a newer unlock (ADR 0012, R24). Listeners are registered synchronously in `background.ts`. `now` is a test seam that no message can set (router row). | `tests/unit/vault/lock-triggers.test.ts` (screen lock, idle, `active` ignored, 900 s interval, alarm at +12 h, alarm clears, other alarms ignored, install-twice, wake: re-arm, exactly-at-hard-max, passphrase-days limit, no wipe of a fresh unlock, no lock on locked vault or unreadable header); `tests/unit/vault/vault.test.ts` (hard-max backstops in `status` and `getDek`, stale-read cases). ADR 0013. Manual: idle and screen-lock firing in real Chrome is not automated. |

## 5. Residual risks recorded in ADRs

Risks that were examined while building Plan 1 and accepted, or that have a rule callers must
follow. Each one is either also listed in §3 or is a new item that §3 does not mention.

| Risk | Why it exists | Mitigation and limit | Where recorded / tested |
|---|---|---|---|
| **DEK bytes in `storage.session` are readable by extension pages** (§3, spec §4.3) | The SW can be killed at any time and must rebuild the unlocked state; the base64 DEK mirror (`vault:session`) is the only place that survives. The string cannot be zeroed, and session storage in RAM may be paged to disk. | `storage.session.setAccessLevel("TRUSTED_CONTEXTS")` is called at SW start, so content scripts cannot read it; mirror is removed on every `lock()`; a malformed mirror reads as locked; the hard max is enforced on rebuild. An XSS in any extension page would still reach it, hence the CSP and sink bans (pages row). Not defended: malware or a memory reader on the machine. | ADR 0012 (session mirror), spec §8.3. Mirror lifecycle: `tests/unit/vault/vault.test.ts` ("session and service-worker restart"). The access-level call itself is only stubbed in `tests/unit/messaging/background.test.ts`; no test asserts its value. Plan 7 should add one. |
| **Idle lock before first unlock and during calibration** | The idle interval is set only once the vault is unlocked, so before that Chrome uses its 60 s default. An idle or screen-lock event that arrives during Argon2 calibration (seconds) wins over `createVault`: the vault is created but left locked, onboarding says "ready" and the popup asks for the passphrase. | Intentional: lock always wins races (ADR 0012, R23), and a locked vault is the safe failure. The result is a retry, not data loss. | ADR 0015 (E2e and idle), ADR 0012. `tests/unit/vault/vault.test.ts` ("lock() during createVault", "lock() during unlock's KDF"); the e2e fixture in `tests/e2e/fixtures.ts` waits out the event. |
| **`withStoreLock` deadlock contract** | JavaScript has no async-local context, so the store cannot tell a call from inside a lock job from an unrelated one. Calling public `setItems`/`removeItems` or nesting `withStoreLock` inside a job queues behind the job and deadlocks the whole store (and so every vault operation) until the worker is killed. Reads are unqueued and can see the state between two `tx` writes. | Documented rule, not a runtime guard: inside a job write only through `tx`, write related keys in one `tx.setItems`, use `tx.getItem` for consistent reads. A closed `tx` rejects, so a leaked handle cannot write. Availability risk only; no confidentiality impact. Reviewers must check any new `withStoreLock` caller. | ADR 0011; JSDoc on `withStoreLock` in `src/lib/store/local.ts`. `tests/unit/store/local.test.ts` (tx inside a job does not deadlock; leaked `tx` rejects; lock released after a throw). The deadlock itself is deliberately not tested. |
| **Unlock holds the store queue for one Argon2 derivation** | Unlock and change-passphrase run inside `withStoreLock` so concurrent guesses see each other's backoff. | Other store writes (for example draft sealing in Plan 5) wait about 0.5–1 s for an unlock, two for a passphrase change. Accepted trade for serialized guesses. | ADR 0012. `tests/unit/vault/vault.test.ts` ("concurrent wrong guesses are serialized"). |
| **Touch ID is not device-bound** (§3) | WebAuthn PRF on macOS comes from iCloud Keychain passkeys, which sync across the Apple ID's devices. Whoever controls the Apple ID and a device on it, plus a copy of the vault data, can unlock without the passphrase. Only Apple Passwords was seen working; 1Password failed to save the passkey. | Optional; passphrase-only stays available and is mandatory at onboarding; the enable screen must disclose the sync and tell the user to choose Apple Passwords. Not built in Plan 1 (Plan 6): `header.prf` is parsed and validated but nothing creates it. A dev key change orphans passkeys (ADR 0003 / 0002). | ADR 0002, `docs/spikes/m0-results.md`. Plan 6: virtual-authenticator e2e. |
| **Backoff is a UI limit, not a defence against offline guessing** | Backoff state lives in `storage.session` (cleared on browser restart) and the check runs in the SW. An attacker with the profile on disk runs Argon2 on their own hardware. | The offline defence is Argon2id at the calibrated cost and the ≥ 12 character rule with a strength meter; backoff only slows guessing through the extension UI and cannot lock the user out for more than 60 s. | ADR 0012, ADR 0001. `tests/unit/vault/backoff.test.ts`. |
| **Integrity check is tamper evidence, not rollback protection** (§3) | A disk-write attacker can restore an older header and its matching older `wrappedDek`, or an older ciphertext record; `vault:integrity` only detects divergent plaintext hints. A lost integrity record makes the vault unopenable without manual recovery (fail closed). | Accepted: write access lets the attacker patch the extension anyway. Failing open would switch the check off. | ADR 0012 (Consequences), spec §8.2/§8.3. `tests/unit/vault/vault.test.ts` ("integrity"). |
| **Wake/unlock timing window** | An unlock that has written its header but not yet its mirror is invisible to a stale-read expiry check; a wake or `status` landing exactly there can lock it. | Result is `locked-during-unlock` and a user retry; needs an expired old session present at the time of a new unlock. | ADR 0013 (Residual window). `tests/unit/vault/lock-triggers.test.ts`, `tests/unit/vault/vault.test.ts` ("lock wins races"). |
| **Best-effort zeroization** | `hash-wasm` leaves the encoded password, intermediate blocks and the 64 MiB matrix in unreferenced memory until GC; only returned buffers are cleared. JS strings (passphrase, base64 DEK) cannot be wiped. | Part of the memory-reader exclusion in §3. Raw DEK bytes and the shared secret are zeroed after use. | ADR 0001, ADR 0012. |
| **Error text and logs** | A message or stack from a failed crypto, KDF or handler call could carry secret-derived text. | Handlers log the request type and error `name` only; the router answers generic `rejected`/`internal`; `DecryptError` has a fixed message and no `cause`. | ADR 0008, 0013, 0014. `tests/unit/messaging/router.test.ts` ("handler exception resolves a generic internal error and logs the name only"). |
