# Threat model

Maintained with the code (spec §8.5). Sections 1–3 are the baseline taken from the design
spec (`docs/superpowers/specs/2026-10-26-refill-design.md` §8.1–§8.3), plus Plan 2 additions that the spec does not have yet (marked where they occur); where they diverge, the spec
is authoritative until this file is updated in the same PR as the change (§ references below point into the spec). Section 4 is a STRIDE
analysis per component of the spec §2 architecture. Rows whose control is not built yet say
"Plan N" in the Test column and are filled in as that plan lands.

## 1. Assets
Saved field values, drafts, passphrase, DEK/KEKs, PRF secret, the list of enabled sites (low).

## 2. Adversaries (in scope)
Hostile web pages; compromised/XSS'd target site; malicious other extensions; local attacker with
**read** access to the browser profile on disk (stolen disk/backup); supply-chain attacker (npm);
hijacked publisher account / malicious update.

A local attacker with **write** access can patch the extension itself and is out of scope, but
cheap tamper-evidence is in scope: the plaintext `draftPub`, lock policy and KDF params are
duplicated inside `vault:integrity` (encrypted, AAD-bound) and compared at every unlock; a mismatch
forces the passphrase path, restores the encrypted values and warns the user. Plaintext values
are treated as hints while locked.

## 3. Out of scope / accepted residual risk
- Malware with OS-level access (keyloggers, memory readers).
- Same-origin honeypots that spec §5.2 does not catch: `mask-image` hiding, opaque
  `pointer-events:none` overlays, covered fields (and covered labels of custom checkbox/radio
  controls) below the fold, font-based masking. They need a hostile same-origin page, which can
  already read filled values (next bullets); step matching limits what they can harvest.
- Plan 2 addition (code analysis; not in the spec yet): `clip-path` is not read by the eligibility
  rules, so a decoy clipped to a small window around the sampled hit-test point can pass; the same
  hostile-same-origin-page reasoning applies. (A submitter's `formaction` was listed here until the
  Plan 2 final review; it is now refused by the fill rules, section 4 `fill/` row.)
- A page disabling Refill on itself: window named access reaches the content script's isolated
  world, so markup such as `<form id="chrome">` replaces the extension API there on a fresh load;
  Refill then does nothing on that page (fails closed, never calls page objects). A page can
  equally hide its fields from the scanner, so this grants it nothing new (ADR 0026).
- Scripts on the *same* origin reading values after Refill fills them. With Auto mode this happens
  without a user action; mitigated (visible, eligible, current-step, once-per-document,
  same-origin form action) to roughly the exposure of typing it yourself. Users can set a profile
  to One gesture.
- DEK raw bytes in `storage.session` RAM may be paged to disk; any Refill extension page can read
  them (see §4.3).
- **Touch ID is not device-bound.** PRF on macOS comes from iCloud Keychain passkeys, which sync
  across the user's Apple ID devices. Anyone who controls the Apple ID (and a device on it) plus a
  copy of the vault data could unlock without the passphrase. Disclosed in the Touch ID enable
  screen; passphrase-only remains available.
- Ciphertext rollback (restoring an older encrypted record) by a disk-write attacker is not
  detected.
- LevelDB may retain deleted ciphertext until compaction (ciphertext only).

## 4. STRIDE per component

S spoofing · T tampering · R repudiation · I information disclosure · D denial of service ·
E elevation of privilege. Repudiation is not applicable to a single-user local tool and is noted
only where an audit trail matters. "Plan N" means the control and its test land in that plan
(Plan 1 foundation, 2 sites and scan/fill, 3 recorder and review, 4 return visit and toast,
5 drafts, 6 pages/design/export, 7 hardening and release).

Status after Plan 1: the rows for `vault/`, `crypto/`, `store/`, `router/`, the lock triggers and
the onboarding/popup pages are built and name the test file that proves each control. Tests are
under `tests/unit/` (`pnpm test`), `tests/e2e/` (`pnpm test:e2e`, real Chromium) and
`tests/manifest/` (`pnpm test:manifest`). Where a control has no automated test yet, the Test
column says so. ADR numbers point into `docs/adr/`.

Status after Plan 2 (sites, scan, match, fill): the rows for `sites/`, the reconciler, the content
script runtime, `fields/` (scanner, eligibility, sensitive-field rules), `match/`, `fill/`, the
content protocol and router content path, the profile store, and the e2e seams are built and name
their proving tests. A fourth test tier was added: `tests/browser/` (`pnpm test:browser`, Vitest
browser mode in real Chromium, ADR 0019) for code that reads a real DOM. Each Plan 2 row ends with
its ADRs. Wording rule for these rows: a control is called enforced only when code, the type
system, a lint rule or a CI gate makes a violation fail; otherwise the row says "by convention".
Open risks of Plan 2 are in section 5.

| **`pathPrefix` is scope, not isolation** | The pathname comes from `sender.url`; same-origin page script can call `history.pushState` to any path before a scan and so obtain the plan of any profile path on its origin. | Later code must not treat the prefix as a security boundary. Segment-boundary matching only prevents accidental application (`/billpay` vs `/billpayment`). | ADR 0025 (Consequences), ADR 0021. `tests/unit/match/match.test.ts` ("profileApplies"); `tests/e2e/fill.spec.ts` ("same origin outside the profile's path prefix (/account) is not filled") proves the accidental case only. |
| **A page can disable Refill on itself** (§3) | Window named access reaches the isolated world: on a document's first load in a tab, `<form id="chrome">` or `<iframe name="chrome">` replaces `chrome` there (verified on Chromium 156; a document reached by navigating within the tab keeps the real globals). | The script starts only if `chrome` is the real runtime and calls nothing it finds by named access, so it fails closed and does nothing on that load. A page can already hide its fields from the scanner, so this grants it nothing new. `browser` markup does not switch Refill off because the content bundle never reads `browser`. | ADR 0026. `tests/browser/content/chrome-api.test.ts`; `tests/manifest/manifest.test.ts`; `tests/e2e/fill.spec.ts` ("page markup named `browser` cannot switch Refill off; `chrome` markup fails closed"). |
| **Decoy classes the eligibility rules do not catch** (§3) | Eligibility samples one point and reads computed style: `clip-path` is not read anywhere in `fields/`, so a decoy clipped to a small window around the sampled point (the centre of the visible part) can pass (code analysis; not in the spec or an ADR yet); `mask-image` hiding and an opaque overlay with `pointer-events: none` pass the hit test; a covered field below the fold is never hit-tested because `elementFromPoint` only runs when the box is in the viewport; font-based masking (`text-security-disc`) is not detected. | These need a hostile same-origin page, which can already read filled values; step matching and once-per-document limit what a decoy can collect. The honeypot e2e fixture covers hidden, off-canvas, `opacity: 0` and covered-in-viewport decoys only. | `mask-image`, overlay and below-fold cases: ADR 0020 (Consequences), spec §8.3. `clip-path`: code analysis only, not yet in the spec or an ADR. (Submitter `formaction` moved to the section 4 `fill/` row: refused since the Plan 2 final review, ADR 0024 amendment.) No test for any of these cases: they are accepted, not defended. |
| **Label proxy below the fold** (§3) | A native checkbox or radio that fails the opacity, size or hit-test checks is eligible through a visible label; the label's hit test cannot run below the fold, so a covered or hidden label there passes. | The exposure is a boolean the user did not see, never a text value. Selects and text controls stay strict. | ADR 0020 (P13, N7). `tests/browser/fields/eligibility.test.ts` ("label proxy runs the control's checks"). The below-fold case is not tested. |
| **Default-port match pattern widens injection** | A match pattern without a port covers every port of the host, and the e2e build relies on this for `https://localhost/*`. The script can therefore also land on another port of an enabled host, or on a granted origin with no site record (after a failed `permissions.remove`, or an injection into a tab that navigated). | The content script is idempotent, and the service worker refuses a content message unless `sender.origin` has an enabled, unrevoked site record and the permission, by exact origin. The script on another port runs a scan and sends a message that is rejected; it never receives a value. | ADR 0018, ADR 0025. `tests/unit/messaging/router.test.ts` and `content-handlers.test.ts` ("another port of an enabled site: rejected even when the permission covers it"). No e2e for another port. |
| **No per-tab scan rate limit** | Each accepted `scan-report` costs a header read, two site-index reads, one AES-GCM open and up to 200 x 300 `scoreSig` calls. Only our content script, or a compromised renderer of an enabled origin, can send. | Parse-before-IO means malformed traffic costs no storage access; the content script debounces to about one report per second per changed fingerprint. Revisit with a per-`tabId`/`documentId` cap. Availability only. | ADR 0025 (Consequences). `tests/browser/content/runner.test.ts` (debounce) and `tests/unit/messaging/content-protocol.test.ts` (parse caps). No test for the flood itself. |
| **Continuous re-scan load and partial scans** | A page that mutates continuously (a clock, an animation) is re-scanned about once a second while the tab is open; a page with more than 50 000 nodes before its form, or more than 300 controls, is partly unscanned. | Scans are bounded by the scanner's budgets (50 000 nodes, 300 controls, 1 200 signatures); `truncated` is reported and the content script never claims a complete page. Partial scans fail closed (nothing fills). | ADR 0023, ADR 0026. `tests/browser/content/runner.test.ts` ("re-scans within the max wait even while the page never stops mutating"); `tests/browser/fields/scan.test.ts` ("scanDocument limits"). |
| **Signatures reveal page structure to the worker** | A scan-report carries name, stable id, autocomplete, type, label text, ordinal and form action path of every eligible non-sensitive control. | Only to the service worker of this extension; never values; sensitive and ineligible controls are not reported. Nothing is sent to any network (no network APIs, CI-gated). | ADR 0025. `tests/browser/content/runner.test.ts` ("reports signatures only"); CI step "Built output has no network APIs". |
| **Revocation or removal in flight** | The sender is authorized before the handler's storage reads and decrypt, so a revoke or `site-remove` landing in those milliseconds does not stop that one reply, and an already-injected content script lives until reload. | The registration is dropped by the reconciler so no new page loads get the script; later messages are rejected by the record check. Bounded to one reply. `accessRevoked` can lag a revocation until a reconcile trigger. | ADR 0018, ADR 0025 (Consequences). `tests/e2e/fill.spec.ts` ("after the site is removed a reload runs no content script and fills nothing"). The in-flight window is not tested. |
| **Prerender path is not tested end to end** | Chromium refuses to prerender while DevTools is attached (`PrerenderingDisabledByDevTools`) and Playwright drives every page through DevTools. | The wait for `prerenderingchange` is tested in browser mode with an injected `isPrerendering`; the default reads the real `Document.prerendering` getter. | ADR 0026. `tests/browser/content/runner.test.ts` ("waits for a prerendered document to be activated"). |
| **The e2e build differs from production** | `pnpm build:e2e` adds `host_permissions: ["https://localhost/*"]` and the `__refillE2E` seams so specs need no permission prompt and can seed profiles. All e2e specs run on this build, not on the shipped one. | Guarded in CI: `check-no-seams.mjs` on the production build, a positive control on the e2e build (must exit exactly 1), and `test:manifest` on the production manifest. The runtime permission-request flow against a fixture site is not exercised end to end. | ADR 0017, ADR 0022. `tests/unit/check-no-seams.test.ts`; CI steps named in the e2e seams row. |
| **`execCommand` dependence** | `document.execCommand("insertText")` is deprecated but is the only way to produce trusted input events from an extension; it is the fallback for masked inputs that revert programmatic writes. | If Chromium removes it the fallback degrades to `rejected-by-page` (reported, nothing written elsewhere).
